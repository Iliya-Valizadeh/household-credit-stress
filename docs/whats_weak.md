# What's weak

The full list of limits. The README shows the top few. They are ranked by how much each
one could change the main result, with the largest first. Each row says what was done
about it, even if the answer is "nothing yet".

All MAE numbers on this page come from a [backtest](glossary.md#backtest) on the latest
[vintage](glossary.md#vintage) of the data (row 4).

| Rank | Weakness | How much it could change the result | What was done |
|---|---|---|---|
| 1 | The `arx` model behind the live one- and three-month ledger forecasts does not beat the AR(1) [baseline](glossary.md#baseline). The test [MAE](glossary.md#mean-absolute-error) gap is 0.03 bp at one month and 0.17 bp at three months, and both [confidence intervals](glossary.md#confidence-interval) include zero (`CLAIMS.md`) | This is the model the ledger grades every month. If it adds nothing over the simplest rule, the ledger's point forecasts carry no proven edge | Kept `arx` and reported the result as it is, rather than swapping in AR(1) to make the headline look better. The verdict field in `reports/metrics.json` shows the result next to the numbers |
| 2 | The scenario engine's `pooled_arx` model (ADR 0004) also fails its own pre-registered twelve- and twenty-four-month check against AR(1): the gap is 1.25 bp at twelve months and 1.64 bp at twenty-four months, and both intervals include zero (`CLAIMS.md`) | This is the model behind every user-drawn scenario path. The result means the stress test's two-year response is not evidence that the drivers forecast anything | Labelled every scenario "Illustrative: not a forecast", per the rule the eval plan fixed before this result was seen (docs/eval_plan.md, "Changes to this plan") |
| 3 | There is no live record yet. The repo has no GitHub remote, so the weekly refresh has never run. `ledger/forecasts.csv` holds one set of forecasts, made from the July 2026 CBA file, and none is graded yet | The ledger is the only fully point-in-time test (docs/eval_plan.md). Until it has graded rows, every result in this repo comes from a backtest | Nothing yet. The ledger code and its append-only and grading tests are in place. The evaluation plan says no claim about beating a baseline is made before there are at least twelve scored origins at a horizon |
| 4 | The CBA archive in `data/raw/cba/` starts with the July 2026 file, so every backtest month uses the latest published vintage. Revisions the CBA, Statistics Canada or the Bank of Canada made to old months, and changes in the CBA's list of reporting banks, are invisible (docs/eval_plan.md) | Backtest numbers could look better or worse than a forecaster working at the time would have done, because the backtest sees the final, revised values. The eval plan expects them to look better | Stated next to the backtest numbers in docs/eval_plan.md, CLAIMS.md, MODEL_CARD.md, the README and this page. Not measured, since no earlier vintage is on hand to compare against |
| 5 | Fitted region by region, the `arx` driver slopes are unstable: at the last fitted origin the mortgage rate slope comes out negative for ATL and MB, the opposite of the expected sign (`reports/metrics.json#model.coefficients_last_origin`) | A per-region model could show a rate rise lowering arrears in those two regions, which no one should believe | The scenario engine pools the slopes across all seven regions instead of fitting one set per region, and drops a wrong-signed driver at each origin (ADR 0004, "the sign rule") |
| 6 | In two regions `arx` is more than a tenth worse than persistence three months ahead, the limit the evaluation plan sets for listing a region here: QC (1.37 bp against 1.22 bp) and AB (1.95 bp against 1.62 bp) (`CLAIMS.md`) | The pooled result hides that `arx` does worse than "no change" in those two regions at three months | Listed here, as the evaluation plan requires. No region is past that limit one month ahead (`reports/metrics.json`, `by_region_test_mae_bp`) |
| 7 | The evaluation plan asks for an append-only log in `reports/` with one row per test run, so the number of attempts is visible. That log was never built | A reader cannot see from the repo how many times the test period was run before each result was committed. The git history of `reports/metrics.json` and `reports/scenario_metrics.json` is the only record | Nothing yet. Listed as a task |
| 8 | The scenario fit drops every row touching March 2020 to December 2021, when payment deferrals kept arrears down while unemployment rose (ADR 0004, "Context") | A future downturn that comes with a deferral program would not look like any scenario this tool can draw | Dropped those rows from the fit, and said in ADR 0004 that every scenario assumes no deferral program |
| 9 | The weekly refresh workflow has never run, since the repo has no GitHub remote yet | Until it runs, the page's copies in `site/data/` and the live ledger only change when someone runs the steps by hand, and the stale label is only as current as the last such run | The workflow now reruns `site_data.py` after `forecast.py` every week and commits it. It also commits when an `ok` or `stale` field in `data/status.json` flips, even with no new data file or ledger row, checked by `refresh_commit.status_flags_changed` (`.github/workflows/refresh.yml`, `tests/test_refresh_commit.py`). The forecast and export steps may fail on their own without failing the run or the commit |
| 10 | The web page's scenario range check (`site/app.js`) only looks at each driver's level, not the `x_u`/`x_m` term the Python engine also checks (`scenario.driver_ranges`, ADR 0004) | Could let the page's "beyond history" warning or hard stop fire at a different point than the Python engine would, in either direction | The page clamps its sliders and warns using the level range only, exported in `site/data/scenario.json`. It never computes or checks the term range |
